## 🎯 Overview

This project implements an end-to-end **Medallion Architecture** on Databricks using:

- incremental ingestion from the public [Open Brewery DB](https://www.openbrewerydb.org/) API;
- Bronze, Silver and Gold data layers;
- simulated Change Data Capture events;
- PySpark cleaning and standardization;
- SCD Type 2 history management;
- Data Quality expectations;
- unit and integration testing;
- Databricks Asset Bundles;
- GitHub Actions CI;
- separate dev, QA and prod environments;
- Databricks Workflows orchestration;
- Slack execution notifications.

The project is designed to reproduce a realistic Data Engineering workflow in which ingestion, transformations, testing, deployment and monitoring are managed as a single version-controlled solution.

# 🥉 Bronze Layer — Paginated API Ingestion

The Bronze layer incrementally ingests data from the Open Brewery DB API.

The current API page is calculated from the number of records already stored in the Bronze table.

## Job Flow

```text
Compute_Page
      │
      ▼
Config
      │
      ▼
Pipeline_Bronze_Ingestion_and_Silver_Ingestion
```

---

## 📓 Task 1 — `Compute_Page`

This notebook calculates the next API page from the number of records already available in `bronze_breweries`.

```python
per_page = 10

try:
    total_existing = spark.table(
        f"{catalog}.{schema}.bronze_breweries"
    ).count()
except Exception:
    total_existing = 0

current_page = (total_existing // per_page) + 1

dbutils.jobs.taskValues.set(
    key="current_page",
    value=current_page
)
```

### Pagination logic

| Existing records | Records per page | Next page |
|---:|---:|---:|
| 0 | 10 | 1 |
| 10 | 10 | 2 |
| 50 | 10 | 6 |

The value is passed to the next workflow task using Databricks task values.

---

## 📓 Task 2 — `Config`

The configuration notebook reads `current_page` and persists it in a Delta configuration table.

```python
current_page = dbutils.jobs.taskValues.get(
    taskKey="Compute_Page",
    key="current_page",
    default=1
)

config_df = spark.createDataFrame(
    [(current_page,)],
    ["current_page"]
)

config_df.write \
    .mode("overwrite") \
    .saveAsTable(
        f"{catalog}.{schema}.bronze_breweries_job_config"
    )
```

The Delta table acts as a bridge between the workflow task and the Lakeflow pipeline.

---

## ⚙️ Bronze Pipeline

The Bronze pipeline reads the current page from the configuration table, calls the API and appends the returned records to `bronze_breweries`.

```python
config_row = (
    spark.table(
        f"{catalog}.{schema}.bronze_breweries_job_config"
    )
    .select("current_page")
    .first()
)

current_page = config_row["current_page"]

response = requests.get(
    "https://api.openbrewerydb.org/v1/breweries",
    params={
        "page": current_page,
        "per_page": 10,
    },
    timeout=30,
)

response.raise_for_status()
data = response.json()
```

The API schema is explicitly declared to guarantee consistent types even when some pages contain columns composed entirely of null values.

# 🔄 CDC Simulation

## 📓 Task — `Creation_Randomic_Data`

The project includes a notebook that generates simulated brewery changes to test the downstream SCD Type 2 process.

The notebook:

- reads existing Bronze records;
- selects a random number of distinct breweries;
- modifies one business attribute;
- assigns a new `ingestion_ts`;
- appends the changed records to `cdc_breweries_events`.

Possible modified columns are:

| Field | Example |
|---|---|
| `phone` | `+1-500-1234567` |
| `street` | `42 Oak Avenue` |
| `name` | `Example Craft Beer` |

The resulting records simulate new versions of existing breweries.

# 🥈 Silver Layer — Staging, Cleaning and Data Quality

The Silver layer combines the original API data with simulated CDC events, applies cleaning rules and validates record quality.

---

## ⚙️ `silver_staging_breweries`

The staging table combines original records and modified versions.

The logical process is:

```text
Original Bronze records
        │
        │ LEFT ANTI JOIN on brewery id
        ▼
Records without a simulated update
        │
        ├──────────────┐
        │              │
        │        CDC records
        │              │
        └──────┬───────┘
               ▼
   silver_staging_breweries
```

Conceptually:

```text
api_filtered =
    bronze_breweries
    LEFT ANTI JOIN
    cdc_breweries_events
    ON id

silver_staging_breweries =
    api_filtered
    UNION ALL
    cdc_breweries_events
```

Each record includes `ingestion_ts`, which is later used to order the SCD Type 2 versions.

---

## 🔧 Reusable PySpark Transformations

The transformation logic is separated from the Lakeflow table declaration.

```text
silver_transformations.py
```

contains the reusable function:

```python
def transform_silver_breweries(
    df: DataFrame
) -> DataFrame:
    ...
```

The function is responsible only for deterministic DataFrame transformations.

Data Quality rules are instead declared in the Lakeflow pipeline through expectations.

This separation makes the transformation independently testable using local PySpark unit tests.

---

## 🔧 Utility Functions

The reusable helper functions are stored in:

```text
src/medallion_dlt_breweries_silver_gold/utilities/utils.py
```

### `clean_phone`

Cleans phone numbers by removing prefixes and non-numeric characters.

Examples:

```text
"+1-800 333-5555" → "8003335555"
null              → "Unknown"
```

### `fill_null`

Replaces null values with a configurable default.

Example:

```text
null → "Doesn't exist"
```

---

## ⚙️ `silver_breweries`

The `silver_breweries` table applies cleaning transformations to `silver_staging_breweries`.

### Transformations

| Field | Transformation |
|---|---|
| `address_2` | Null values replaced with `"Doesn't exist"` |
| `address_3` | Null values replaced with `"Doesn't exist"` |
| `name` | Removes the `Â` encoding artifact |
| `phone` | Removes prefixes and non-numeric characters |
| `postal_code` | Removes the ZIP+4 suffix for US records |
| `brewery_sk` | SHA-256 hash generated from `id` and `ingestion_ts` |

The surrogate key is generated using:

```python
F.sha2(
    F.concat_ws(
        "_",
        F.col("id"),
        F.col("ingestion_ts").cast("string")
    ),
    256
)
```

This produces a deterministic key for each brewery version.

# ✅ Data Quality Expectations

Data Quality rules are applied directly to the Silver Lakeflow table.

They are intentionally separated from the PySpark transformation function so that invalid records can be measured by the pipeline before being dropped or rejected.

## Implemented expectations

| Expectation | Rule | Behavior |
|---|---|---|
| `valid_brewery_id` | `id IS NOT NULL` | Fails the pipeline update |
| `valid_ingestion_timestamp` | `ingestion_ts IS NOT NULL` | Fails the pipeline update |
| `valid_country` | `country = 'United States'` | Drops invalid records |
| `valid_primary_address` | `address_1 IS NOT NULL` | Drops invalid records |
| `valid_brewery_name` | Name is not null or empty | Records the violation |
| `valid_brewery_type` | `brewery_type IS NOT NULL` | Records the violation |

Example:

```python
@dp.table(
    name="silver_breweries",
    comment="Cleaned brewery data with Data Quality expectations",
)
@dp.expect_or_fail(
    "valid_brewery_id",
    "id IS NOT NULL",
)
@dp.expect_or_fail(
    "valid_ingestion_timestamp",
    "ingestion_ts IS NOT NULL",
)
@dp.expect_or_drop(
    "valid_country",
    "country = 'United States'",
)
@dp.expect_or_drop(
    "valid_primary_address",
    "address_1 IS NOT NULL",
)
@dp.expect(
    "valid_brewery_name",
    "name IS NOT NULL AND trim(name) <> ''",
)
@dp.expect(
    "valid_brewery_type",
    "brewery_type IS NOT NULL",
)
def silver_breweries():
    source_df = spark.read.table(
        silver_staging_table
    )

    return transform_silver_breweries(source_df)
```

## Expectation behavior

```text
expect
→ Records the violation but keeps the record

expect_or_drop
→ Records the violation and drops the invalid record

expect_or_fail
→ Stops the pipeline update when the rule is violated
```

The pipeline exposes expectation metrics such as passed, failed and dropped records.

Aggregate quality checks, such as duplicate detection, remain in the integration validation notebook because they require comparisons across multiple records.

# 🥇 Gold Layer — SCD Type 2 and Aggregations

## ⚙️ `gold_breweries`

The Gold layer implements **Slowly Changing Dimension Type 2** using Lakeflow AUTO CDC.

```python
dp.create_auto_cdc_flow(
    target="gold_breweries",
    source="silver_breweries_stream",
    keys=["id"],
    sequence_by=F.col("ingestion_ts"),
    stored_as_scd_type=2,
    except_column_list=["ingestion_ts"],
)
```

Each brewery can therefore have multiple historical versions.

## Generated SCD Type 2 columns

| Column | Description |
|---|---|
| `__START_AT` | Timestamp from which the version is valid |
| `__END_AT` | Timestamp at which the version stops being valid |
| `__END_AT IS NULL` | Identifies the currently active version |

The brewery business key is:

```text
id
```

The version ordering column is:

```text
ingestion_ts
```

---

## ⚙️ `agg_breweries`

The aggregation table uses only the currently active Gold records.

```python
(
    gold_df
    .where(F.col("__END_AT").isNull())
    .groupBy("state")
    .agg(
        F.count("brewery_sk").alias("num_breweries"),
        F.countDistinct("brewery_type").alias("num_types"),
    )
    .orderBy(F.col("num_breweries").desc())
)
```

## Output columns

| Column | Description |
|---|---|
| `state` | US state |
| `num_breweries` | Number of active breweries |
| `num_types` | Number of distinct brewery types |

# 🧪 Testing Strategy

The project uses two complementary testing levels.

```text
Unit tests
→ Test isolated PySpark functions locally

Integration test
→ Validate deployed tables and cross-table business rules
```

---

## 🧪 Unit Tests

Unit tests are implemented with:

- `pytest`;
- a local SparkSession;
- explicit Spark schemas;
- reusable PySpark transformation functions.

The test SparkSession is created once per test session in:

```text
tests/conftest.py
```

The tests verify:

- phone normalization;
- null replacement;
- name cleaning;
- postal code normalization;
- surrogate-key generation;
- preservation of the expected number of records.

Run the unit tests locally with:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pytest tests\unit -v
```

The Silver unit test uses only valid input records because Data Quality filtering is now handled by Lakeflow expectations rather than by the reusable transformation function.

---

## 🔎 Integration Test

The integration test is implemented in:

```text
src/validation/test_integration_validate_pipeline.ipynb
```

It runs as the `Integration_Test` workflow task after the Silver and Gold pipeline.

The notebook validates:

- existence of the expected tables;
- non-empty Silver and Gold tables;
- required columns;
- non-null surrogate keys;
- duplicate combinations of `id` and `ingestion_ts`;
- SCD Type 2 consistency;
- a single current Gold version per brewery;
- validity of `__START_AT` and `__END_AT`.

The workflow passes the environment-specific catalog and schema through notebook parameters.

```yaml
base_parameters:
  catalog: ${resources.schemas.breweries_schema.catalog_name}
  schema: ${resources.schemas.breweries_schema.name}
```

When all validations pass, the notebook prints:

```text
INTEGRATION TEST COMPLETATO CON SUCCESSO
```

The message is visible in the output of the `Integration_Test` task in the Databricks workflow run.
